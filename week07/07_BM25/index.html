    검색 품질 — Kiwi+BM25, Dense 비교¶

    원본 코드: 07_BM25.py

    Kiwi 형태소 분석 — 한글을 형태소 단위로 쪼개기¶

    조사·어미가 붙어도 같은 단어면 같은 형태소로 인식하게 만드는 게 목적임.
    BM25는 문자열이 완전히 같아야 매칭되는데, 한국어는 어미 변화가 심해서 형태소 분석 없이
    그냥 BM25 돌리면 '연차를'과 '연차'를 다른 단어로 취급해버림.

    from kiwipiepy import Kiwi

kiwi = Kiwi()

# Token 객체
def kiwi_tokenize(text):
    return [token.form for token in kiwi.tokenize(text)]

# 결과
for word in ["공개했다", "공개하고", "공개된"]:
    print(word, "→", kiwi_tokenize(word))
    Token 객체에는 form(형태소 원형), tag(품사), 위치정보(start, len) 가 있음
    공개했다 → ['공개', '하', '었', '다']
    공개하고 → ['공개', '하', '고']
    공개된 → ['공개', '되', 'ᆫ']

    사전에 없는 복합명사는 갈라짐

    '반차를'을 넣어보니 ['반', '차', '를']로 쪼개짐. '반차'가 한 형태소로 안 나오고
    '반' + '차'로 갈라짐 — Kiwi 사전에 '반차'가 복합명사로 안 실려 있어서 그런거임.

    Kiwi 토큰을 BM25Retriever에 연결하기¶

    Kiwi로 쪼갠 형태소 리스트를 BM25Retriever의 preprocess_func 자리에 꽂아주면,
    색어와 문서 둘 다 같은 방식으로 토큰화된 뒤 BM25 점수가 계산됨.

    from langchain_community.retrievers import BM25Retriever
from langchain_core.documents import Document

manual_documents = [
    "연차를 신청하려면 인사 포털에서 승인 요청을 등록합니다.",
    "반차를 사용하려면 팀장 승인이 필요합니다.",
    "연차 잔여일은 급여 시스템에서 확인합니다.",
    "출장을 신청하려면 경비 포털에 등록합니다.",
    "회의실 예약은 협업 도구에서 진행합니다.",
    "보안 교육은 분기마다 이수합니다.",
]


kiwi_documents = [Document(page_content=text) for text in manual_documents]
kiwi_query = "연차를 신청하려면 어떻게 해야 하나요?"

# 임베딩 없이 단어 일치와 희소성을 이용하는 키워드 검색기 생성
bm25 = BM25Retriever.from_documents(
    kiwi_documents,
    preprocess_func=kiwi_tokenize,
)

# (참고) k 의 기본값은 4임
bm25.k = 2

hits = bm25.invoke(kiwi_query)
for rank, doc in enumerate(hits, start=1):
    print(rank, doc.page_content)

assert hits[0].page_content == manual_documents[0]
    preprocess_func 자리에 검색어·문서 둘 다에 적용할 토큰화 함수를 넣음.
    토큰화 함수를 넣지 않으면 기본 전처리(공백 분리 + 소문자화)가 쓰이는데,
    그러면 한국어 조사가 안 걸러져서 '연차'와'연차를'을 다른 단어로 취급함

    조사가 붙어도 매칭됨

    질문엔 '연차를 신청'만 있고 '반차'·'잔여일' 얘긴 없는데도 BM25가 1위를 정확히 골라냄.
    Kiwi가 '연차를'을 ['연차', '를', ...]로 쪼개니까 조사가 붙어도 '연차'라는 형태소 자체가
    그대로 매칭되기 때문임.

    preprocess_func이 metadata도 토큰화하는지?

    궁금했던것 → preprocess_func이 metadata도 토큰화하는지?
    document.page_content만 뽑아서 preprocess_func에 넣고, metadata는 그냥 옆에 보관만 함
    검색 시 query도 마찬가지로 page_content 쪽 토큰이랑만 비교됨
    테스트 해 본 결과: metadata에만 검색어를 넣어둔 문서는 안 걸리고, page_content에 실제로 검색어가 있는 문서만 1등으로 나옴
    즉 metadata는 검색엔 전혀 관여 안 하고, 결과로 받을 때 부가정보(h.metadata["page"]처럼)로만 쓰임.

    filter·where_document 는 에러 없이 무시됨

    궁금했던것 -> filter나 where_document(Chroma에서 쓰던 메타데이터 필터링)도 BM25에서 사용가능한지?
    예상대로 안되지만 filter 나 where_document 인자 넣어도 에러가 나지 않으니 주의해야 함.

    PDF 청크 + Dense 벡터스토어 준비¶

    import os

# 로컬 캐시에 받아둔 모델만 쓰겠다는 옵션.
os.environ["HF_HUB_OFFLINE"] = "1"


from langchain_huggingface import HuggingFaceEmbeddings
from langchain_chroma import Chroma
from langchain_community.document_loaders import PyPDFLoader
from langchain_text_splitters import RecursiveCharacterTextSplitter

embedding = HuggingFaceEmbeddings(model_name="BAAI/bge-m3")

# 재연결
vectorstore = Chroma(
    collection_name="ai_brief",
    embedding_function=embedding,
    persist_directory="./chroma_ai_brief",
)

pages = PyPDFLoader("SPRi_AI_Brief_8월호.pdf").load()
docs = RecursiveCharacterTextSplitter(
    chunk_size=800, chunk_overlap=150
).split_documents(pages)

    BM25Retriever 생성¶

    bm25 = BM25Retriever.from_documents(docs, preprocess_func=kiwi_tokenize)
bm25.k = 2

dense = vectorstore.as_retriever(search_kwargs={"k": 2})

    Dense vs BM25 — 실패 유형이 다르다¶

    질문 단어와 문서 단어가 안 겹치는 '의미형' 질문에서는 BM25가 정확도가 낮음.
    반면, 고유명사가 포함된 질문은 BM25가 정답 문서를 정확하게 잘 찾음.

    # q1은 의미형 질문 예시임
q1 = "AI 모델이 답변 전에 따로 처리한 흔적은?"

for h in dense.invoke(q1):
    print(h.metadata["page"], h.page_content[:55])


for h in bm25.invoke(q1):
    print(h.metadata["page"], h.page_content[:55])

# q2는 단어 매칭 질문 예시임
q2 = "Sakana Fugu는 무엇인가요?"

for h in dense.invoke(q2):
    print(h.metadata["page"], h.page_content[:55])

for h in bm25.invoke(q2):
    print(h.metadata["page"], h.page_content[:55])

    Dense가 항상 BM25보다 나은 거 아닌가

    헷갈렸던 것 → "Dense가 의미 검색이니까 항상 BM25보다 낫겠지"라고 생각했는데 아니었음.
    'Sakana Fugu' 같은 드문 고유명사는 BM25가 구조적으로(글자가 그대로 있으니)
    항상 맞히는 게 보장되는 반면, Dense는 임베딩 모델이 학습 때 못 본 표기면 흔들릴 수 있음.
    이번엔 우연히 Dense도 맞혔을 뿐 항상 보장되는 게 아님.
    결론: 두 검색기는 실패 유형이 다름 → 섞으면 서로의 빈틈을 메울 수 있음.

    RRF(Reciprocal Rank Fusion) — 개념만 정리¶

    종류가 다른 검색기를 섞을 때 사용 하는 기법
    키워드 검색 점수는 수십 단위(예: 21.4)고 의미 검색 점수는 0~1 사이(예: 0.88)임.
    두 점수를 그대로 더하면 안 됨 → 점수 "단위"가 달라서 큰 쪽(BM25)이 결과를 지배해버림.
    RRF는 원점수를 아예 버리고 "몇 등이었는지"(순위)만 사용해서 이 문제를 피함.

    공식: RRF_score(문서) = Σ 1 / (등수 + k)

여러 검색기에서 같은 문서가 나오면 각 검색기에서 받은 점수를 더함. 
k는 상수(보통 60)
k가 작으면(k=1) 1등과 2등 사이 점수 차이가 크게 벌어지고,
k가 크면(k=60) 등수 차이의 영향이 완만해져서 "여러 검색기에 공통으로 등장한 문서"가 상대적으로 유리해짐.

EnsembleRetriever 에서는 여기서 설명한 k가 c인자임.

    원점수 합산 vs RRF

    예시) 키워드 검색 1위 'VPN 접속 오류 해결'(21.4점), 의미 검색 1위 '재택근무 중 사내망 연결 문제 해결'(0.88점)
    - 원점수를 그냥 더하면: 의미 검색 1위 문서가 21.4라는 큰 수에 묻혀서 전체 5위로 밀림
    - RRF(k=60)로 합치면: 3위로 올라옴 — 등수만 보니까 원점수 크기 차이가 사라진 덕분
    처음엔 "그냥 두 점수를 정규화(0~1로)해서 더하면 되는 거 아닌가" 싶었는데, RRF는 정규화조차 필요 없다는 게 포인트임
    등수만 쓰니까 애초에 점수 스케일을 맞출 필요가 없어짐 — 그래서 실무에서 종류가 다른 검색기를 섞을 때 RRF를 많이 씀.

    EnsembleRetriever — 가중 RRF로 하이브리드 검색기¶

    LangChain에서는 RRF를 직접 구현할 필요 없이 EnsembleRetriever가 대신 계산해줌.
    retrievers 목록과 weights(가중치)만 넘기면 내부에서 가중 RRF로 순위를 합침.

    from langchain_classic.retrievers import EnsembleRetriever

# weights는 retrievers 리스트와 같은 순서로 대응함 — [bm25 가중치, dense 가중치].
hybrid = EnsembleRetriever(retrievers=[bm25, dense], weights=[0.5, 0.5])

q1 = "AI 모델이 답변 전에 따로 처리한 흔적은?"
q2 = "Sakana Fugu는 무엇인가요?"

for q in [q1, q2]:
    for rank, h in enumerate(hybrid.invoke(q)[:3], 1):
        print(rank, h.metadata["page"], h.page_content[:52])
    둘의 합이 반드시 1일 필요는 없음(그냥 비율로 곱해지는 값)

    가중치 튜닝 — 질의 유형에 맞게 조정¶

    반반 가중치가 항상 최선이 아님. 서비스에 어떤 질문이 많이 들어오는지에 맞춰
    weights를 실험으로 조정해야 함.

    # 의미형 질문이 많은 서비스 라고 가정 하고 Dense를 우대하는 쪽으로 튜닝
hybrid_tuned = EnsembleRetriever(retrievers=[bm25, dense], weights=[0.3, 0.7])

for q in [q1, q2]:
    for rank, h in enumerate(hybrid_tuned.invoke(q)[:3], 1):
        print(rank, h.metadata["page"], h.page_content[:52])

    weights 는 실험으로 정하는 값

    여기서 배운 것 → 하이브리드 검색은 "BM25+Dense 섞으면 무조건 더 좋아짐"이 아니었음.
    가중치를 잘못 잡으면(반반) Dense 단독보다 오히려 나빠질 수 있고, 내
    서비스에 어떤 질문이 많이 들어오는지(의미형이 많은지 고유명사형이 많은지)에
    맞춰 weights를 실험으로 정해야 함. 청킹할 때 chunk_size=800/overlap=150을
    정한 것처럼, 이것도 정답이 정해진 값이 아니라 튜닝 대상임.

    궁금했던거 - EnsembleRetriever엔 k 설정이 없는데 결과가 몇 개 나오는지?¶

    - 확인해보니 클래스 필드 자체에 k가 없었음(retrievers, weights, c, id_key뿐)
- 대신 이렇게 동작함:
  1. BM25가 k개, Dense가 k개를 각각 가져옴
  2. 중복 제거 전에 문서별 RRF 점수부터 먼저 계산
     — 같은 문서(page_content 기준)가 두 검색기에서 다 나왔으면 점수를 누적해서 더함
     (공통으로 뜬 문서를 우대하는 RRF 핵심 로직이라 dedup보다 점수 계산이 먼저 일어나야 함)
  3. 그다음 중복 제거
     (같은 page_content면 먼저 나온 것 하나만 남기고, 점수는 이미 합쳐진 채로 유지)
  4. 남은 문서를 점수순으로 정렬해서 "자르지 않고 전부" 반환

    결과 개수는 이렇게 정해짐

    즉 결과 개수는 k*검색기 수(겹치는 게 하나도 없을 때 최댓값)에서, 두 검색기가 겹쳐 찾은 만큼 빠짐.
    (k=3+k=3 두 BM25 조합): 완전히 겹치면 3개, 하나도 안 겹치면 6개,
    서로 다른 문서인데 page_content(본문 글자)가 우연히 똑같아도 dedup 기준이
    page_content라서 1개로 합쳐짐
